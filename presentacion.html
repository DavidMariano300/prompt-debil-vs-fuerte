Empate honesto · los dos escapan el HTML antes de pintar datos del servidor, así que ninguno es vulnerable a XSS en la tabla de usuarios.

05

Conclusión · Resumen ejecutivo

Los dos proyectos funcionan. La diferencia no es si compilan, sino cuánto trabajo queda pendiente antes de poder desplegarlos. El prompt débil entrega un prototipo; el prompt fuerte entrega un entregable.

Ahorra tiempo

Menos iteraciones de ida y vuelta

Pedir logs, README, validaciones y manejo de errores en el primer prompt evita 4 o 5 rondas de «ahora añádele…». El código de ./Fuerte es 86 % más extenso, pero ese volumen es justamente el trabajo que en ./Debil tendrías que escribir tú después.

Evita fallos

La seguridad no se improvisa

Un secreto JWT sin validar, cero try/catch y datos personales dentro del token son riesgos que nadie detecta probando la app: solo aparecen en producción. El prompt fuerte los cierra porque el requisito estaba escrito desde el inicio.

Listo para producción

Operable desde el día uno

Logs con timestamp e IP, aviso claro si el puerto está ocupado, apagado ordenado de la base de datos y un README que documenta cada endpoint. Es la diferencia entre un demo y algo que otra persona puede mantener.

La regla: el modelo no adivina tus estándares de calidad. Especifica criterios verificables —hashing, validación de configuración, formato de logs, manejo de errores, documentación— y obtendrás código listo para revisión, no un punto de partida.
